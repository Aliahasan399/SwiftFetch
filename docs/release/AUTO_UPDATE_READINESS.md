## 3. Exact owner steps to activate later (from `UPDATER_KEY_SETUP.md`)

These are **not performed**. They are reproduced so the owner can execute them at the appropriate
time. No endpoint URL, key, or identity is invented here.

### Step A — Generate the signing key pair locally (`UPDATER_KEY_SETUP.md` §3)
Run from the project root; choose and store a passphrase in a password manager.
```powershell
npm run tauri -- signer generate -- -w "$env:USERPROFILE\.tauri\swiftfetch.key"
# or: npx tauri signer generate -- -w "$env:USERPROFILE\.tauri\swiftfetch.key"
# or: minisign -G -p "$env:USERPROFILE\.tauri\swiftfetch.pub" -s "$env:USERPROFILE\.tauri\swiftfetch.key"
```
Keep the private key (`swiftfetch.key`) and passphrase offline and never commit them; only the
**public** key string may be embedded.

### Step B — Fill the three channel values together (`§4`)
```powershell
$env:SWIFTFETCH_UPDATE_ENDPOINT   = 'https://[OWNER]/[HOST]/releases/latest/download/latest.json'
$env:SWIFTFETCH_UPDATE_ARCHIVE    = 'https://[OWNER]/[HOST]/releases/download/v{{version}}/latest.json'
$env:SWIFTFETCH_UPDATE_PUBLIC_KEY = (Get-Content -Raw "$env:USERPROFILE\.tauri\swiftfetch.key.pub").Trim()
$env:TAURI_SIGNING_PRIVATE_KEY_PATH     = "$env:USERPROFILE\.tauri\swiftfetch.key"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = '[OWNER: key passphrase]'  # only if required
./tools/build-windows.ps1
```
Set **all three or none** — a partial configuration fails the build (`build-windows.ps1:19-25`).
Prefer `_PATH` over key contents. `build-windows.ps1` adds `createUpdaterArtifacts = true` and emits
`.sig` artifacts; builds run `--ci --locked`.

### Step C — Approve an HTTPS host and publish (§4, §6)
Choose and approve a concrete HTTPS host before filling the endpoint variables. GitHub Releases can
serve at zero cost for a public repository. Prepared (not activated) templates:
- `SWIFTFETCH_UPDATE_ENDPOINT` → `https://github.com/[OWNER]/[REPO]/releases/latest/download/latest.json`
  or pinned `…/releases/download/v0.1.0/latest.json`
- `SWIFTFETCH_UPDATE_ARCHIVE` → `https://github.com/[OWNER]/[REPO]/releases/download/v{{version}}/latest.json`

A real repository URL is recorded as a candidate host in
`docs/release/AUTO_UPDATE_EXECUTION_REPORT.md:59-72`; **it is a plan, not an activated endpoint.**

### Step D — Produce the signed manifest (§5, `release-channel.ps1`)
```powershell
./tools/release-channel.ps1 `
  -ArtifactBaseUrl 'https://[OWNER]/[HOST]/releases/download/v0.1.0' `
  -Installer 'src-tauri/target/release/bundle/nsis/SwiftFetch_0.1.0_x64-setup.exe' `
  -Notes 'SwiftFetch 0.1.0 Windows update'
```
Verify `latest.json` has a single `windows-x86_64` entry, the exact HTTPS installer URL, the base64
`.sig`, and `version: 0.1.0` (binding enforced at `release-channel.ps1:14-22`). Publish the manifest,
installer, and `.sig` to the approved host **only after release approval**. Preserve per-version
assets for as long as clients need rollback (`:174-179`).

### Step E — Clean-VM end-to-end validation (before claiming updates work)
With real signed artifacts and the activated endpoint, exercise on a disposable Windows VM:
detection, download, signature/signed-version verification, NSIS/MSI install, health check,
automatic rollback on failure, explicit rollback, and startup reconciliation. Record evidence.
Until this is done, no end-to-end claim is valid.
