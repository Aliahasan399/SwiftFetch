# SwiftFetch — GitHub Releases-compatible structure (version 0.1.0)

**Status:** procedure document only. **No publication is performed by this repository or by the
agent.** Nothing here creates a GitHub release, uploads an asset, tags a commit, or activates an
update endpoint. All actions below are manual steps for the release owner.

Owner decisions recorded by the parent lane (used only for framing, not invented):
individual/personal publisher, proposed license **GPL-3.0-or-later**, **free download**, **zero
budget**. No support contact, legal name, or other identity is invented here — every such value is
left as `[OWNER: …]` for the owner to fill locally.

GitHub Releases is compatible with a zero-budget, free, public distribution: a public repository
can host unlimited release assets and checksum files over HTTPS at no cost. A private GitHub
account can publish public releases without a paid plan. This document describes the exact asset
names and safe process; it does not claim that a release exists or is authorized.

Notes on naming:

- The version in `src-tauri/tauri.conf.json` and `package.json` is **`0.1.0`** (no `v` prefix).
  The installer names are generated by Tauri from that value: `SwiftFetch_<version>_x64-setup.exe`
  and `SwiftFetch_<version>_x64_en-US.msi` (see `tools/stage-release.ps1:19-20`).
- **Do not rename** the exe or msi when attaching them. The updater's installer staging checks the
  `.msi` extension (`src-tauri/src/updates.rs:438`) and the release tooling constructs these exact
  names. Renaming can break update/rollback handling and checksum verification.
- The source zip name `SwiftFetch-0.1.0-source.zip` comes from `tools/package-source.ps1:44`. Its
  allowlist excludes `.key/.pfx/.p12`, databases, downloads, `target/`, `dist/`, `node_modules/`,
  and `*.bak-*` files (`tools/package-source.ps1:38-39`), so it is suitable as a public source
  artifact **after** license approval.
- The staging tool also emits `release-manifest.json`
  (`artifacts/release/SwiftFetch-0.1.0-windows-x64/`) containing `product`, `version`, `platform`,
  `publisher_thumbprint`, and per-file `name`/`size`/`sha256`. It may be attached as additional
  evidence, but it is not required by GitHub Releases.

## 2. Tag conventions

- Recommended git tag: **`v0.1.0`** (annotated tag, e.g. `git tag -a v0.1.0 -m "SwiftFetch 0.1.0"`).
  This is a convention only; no tag is created by this document.
- The application version string remains **`0.1.0`** in config and in asset filenames.
- If a `v`-prefixed tag is used, any update-channel URL template that points at GitHub release
  download paths must include that prefix, e.g. use
  `https://github.com/[OWNER]/[REPO]/releases/download/v{{version}}/…` so that `{{version}}`
  (`0.1.0`) resolves to the real tag `v0.1.0`. The updater substitutes `{{version}}` with
  `CARGO_PKG_VERSION`, and also supports `{{current_version}}`, `{{target}}` and `{{arch}}`
  (`src-tauri/src/updates.rs:103-106`). Mismatched tag/version prefixes are a common cause of
  404s — verify the resolved URL with a browser before announcing a release.
- Do not move or delete a tag after assets are attached. Immutable, version-pinned URLs are what
  the updater archive endpoint relies on (see `UPDATER_KEY_SETUP.md`).

## 3. Attaching assets to a GitHub release

Manual steps for the owner, after all release gates in `RELEASE_PLAN.md` / `GO_NO_GO_REPORT.md`
are closed and the owner has explicitly approved publication:

1. Create the release from the `v0.1.0` tag on the public GitHub repository; leave it as a draft
   until the checklist in §6 passes.
2. Set the release title to something factual such as `SwiftFetch 0.1.0 (Windows x64)` and mark it
   as a normal (not pre-release/draft) release only at publication time. Do not check "set as the
   latest release" until approval.
3. Paste the release notes from `CHANGELOG.md` (`## 0.1.0 — Windows candidate`). Keep the existing
   caveat that signing, licensing, store approval, and clean-machine acceptance are separate
   concerns; do not edit the changelog to imply they are complete.
4. Attach, with exactly these display names:
   - `SwiftFetch_0.1.0_x64-setup.exe`
   - `SwiftFetch_0.1.0_x64_en-US.msi`
   - `SwiftFetch-0.1.0-source.zip`
   - `SHA256SUMS` (covering the three files above; see §4)
   - optionally `release-manifest.json`
5. If and only if the updater channel is later configured and approved, also attach the signed
   updater manifest and signature artifacts (see `UPDATER_KEY_SETUP.md`). **Do not attach or
   activate updater artifacts before owner approval.**
6. Save as draft; perform §6; then publish.

## 4. SHA256SUMS — generation and format

The tooling already writes two-space-separated lines with lowercase hex
(`tools/stage-release.ps1:47-48`, `tools/package-source.ps1:46-47`), the standard `sha256sum` layout:

```
<64-char-lowercase-hex>  SwiftFetch_0.1.0_x64-setup.exe
<64-char-lowercase-hex>  SwiftFetch_0.1.0_x64_en-US.msi
<64-char-lowercase-hex>  SwiftFetch-0.1.0-source.zip
```

The owner should regenerate `SHA256SUMS` from the **final exact files that will be uploaded**,
not from intermediate builds, and verify that after upload the GitHub asset checksums match.
PowerShell equivalent (run locally, read-only hash computation):

```powershell
Get-FileHash -LiteralPath 'SwiftFetch_0.1.0_x64-setup.exe' -Algorithm SHA256
Get-FileHash -LiteralPath 'SwiftFetch_0.1.0_x64_en-US.msi' -Algorithm SHA256
Get-FileHash -LiteralPath 'SwiftFetch-0.1.0-source.zip' -Algorithm SHA256
```

## 5. Checksum verification instructions for users (to include in release notes)

Provide these verbatim so a downloader can verify integrity independently. Replace `[OWNER]` /
`[REPO]` locally; do not leave placeholders in a published release.

> After downloading the installer and `SHA256SUMS` from the same release page, verify before
> running the installer.
>
> **Windows PowerShell:**
> ```powershell
> # From the folder containing the downloaded files
> Get-Content .\SHA256SUMS
> Get-FileHash .\SwiftFetch_0.1.0_x64-setup.exe -Algorithm SHA256
> ```
> Compare the `Hash` value (case-insensitive) with the line for that filename in `SHA256SUMS`.
> They must match exactly.
>
> **Windows Command Prompt (alternative):**
> ```
> certutil -hashfile SwiftFetch_0.1.0_x64-setup.exe SHA256
> ```
>
> If any hash does not match, **do not run the installer** — delete the file and report it to the
> publisher through the support channel documented by the owner. A matching checksum proves the
> file is the one published, not that the publisher is trusted; Authenticode/ code-signing trust is
> a separate property (see `SIGNPATH_ELIGIBILITY.md` and `OWNER_CONFIG_GUIDE.md`).
