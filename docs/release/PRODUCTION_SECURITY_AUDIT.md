## Findings and recommendations

All findings are **observed weaknesses, documentation gaps, or residual risks** — none is evidence of a successful exploit. No finding here should be read as a certification pass or fail.

### F1 — Native-messaging trust boundary is syntactic; shipped manifest template is inconsistent with the active host — **Low** (defense-in-depth / packaging)

*Evidence:* `src-tauri/src/native_host.rs:60-71` accepts a caller when the first argument merely *looks* like a chrome-extension origin (a 32-character `[a-p]` id) or an absolute Firefox manifest path plus the fixed `FIREFOX_ID`. It does not cryptographically prove the caller. The real caller allowlist is the browser's native-messaging `allowed_origins`, which the acceptance harness correctly pins to one concrete extension id (`tools/test-browser-registration.ps1:5,16-17`).
Meanwhile the in-repo template `browser-extension/native-host/com.swiftfetch.app.json:4,7` still points at the Python `.bat` launcher and uses the placeholder `chrome-extension://PASTE_YOUR_EXTENSION_ID_HERE/`. The Python host `host.py:524-567` authenticates its loopback POST with an HMAC shared secret, but the active Rust host reads framed stdin directly (`native_host.rs:168-179`) and this codebase contains **no** loopback listener implementing that HMAC bridge (no match for `27642`/`X-SwiftFetch-Signature` in `src-tauri/src`). The Rust direct-stdio path therefore has no HMAC equivalent.
*Impact:* A local process could launch the native-host executable with a spoofed `chrome-extension://…` argument and pipe a crafted intent; this can queue a download into the configured downloads folder (filename/path still sanitized; `browser_integration` must be enabled). It cannot read secrets back through this path. Primary impact is a weakened defense-in-depth boundary plus operator confusion about which manifest/host is authoritative. The placeholder id fails closed (no extension can connect) but is a deployment trap.
*Recommendation:* (1) Align the shipped manifest template with the Rust executable and document the one-time substitution of the real extension id; (2) mark the Python/HMAC bridge clearly as legacy/non-shipping, or if it is intended to ship, add the corresponding authenticated loopback listener; (3) optionally add a shared secret to the direct-stdio path and document that the browser is the trusted broker.

### F2 — Updater public key lives only in compile-time env; plugin config `pubkey` is empty — **Low** (reviewability / fail-safe clarity)

*Evidence:* `src-tauri/tauri.conf.json:31` contains `"pubkey": ""` while signature verification relies on `option_env!("SWIFTFETCH_UPDATE_PUBLIC_KEY")` baked into the binary (`updates.rs:54-61,92-100`). `requireSignedVersion` is correctly `true` (`tauri.conf.json:31`). `tools/build-windows.ps1:19-25` requires all three channel variables and a signing key, and disables updater artifact creation otherwise. If the key is absent at compile time, `publisher()` returns `None` and updates are silently disabled (fail-safe) — but a reviewer looking only at `tauri.conf.json` could wrongly conclude signing is unconfigured.
*Recommendation:* Document explicitly that the config `pubkey` is intentionally empty and the key is injected at build time; keep `requireSignedVersion: true`; add a release-gate assertion that a configured channel has a non-empty compiled pubkey (already partially enforced in `build-windows.ps1`).

### F3 — Predictable `.part` path opened without exclusive/create-new semantics — **Low** (local-only residual risk)

*Evidence:* `run_writer` opens the task-owned partial with `.create(true).write(true).truncate(truncate)` (`engine.rs:2762-2767`). The path is derived from the (sanitized) destination plus a sanitized task-id token (`engine.rs:2615-2670`), so it is predictable to a local observer. There is no `create_new`/`O_NOFOLLOW` on first creation.
*Impact:* A local attacker who already has write access to the downloads directory could pre-create or replace that file (e.g. a symlink) to redirect bytes. This requires local filesystem write access, which already implies a broader compromise, and the final destination is still constrained by `resolve_destination` and the no-clobber publish.
*Recommendation:* Open with `create_new(true)` on the first write (falling back to append on resume) or place working files in a private per-user temp directory; re-check that the opened inode is a regular file. Track as residual risk, not a confirmed exploit.

### F4 — Stale security-relevant code comment — **Informational**

*Evidence:* `commands.rs:490-491` states that `encrypt_saved_secrets` must be registered in `lib.rs -> generate_handler!` and was "reported to the parent agent", but it **is** registered at `lib.rs:356`.
*Impact:* No functional or security impact; documentation drift that could mislead a reviewer into thinking the opt-in encryption command is unreachable.
*Recommendation:* Remove or update the stale comment; keep the command registered.

## Summary

All thirteen audited control areas (C1–C13) are **implemented in source** with concrete `file:line` evidence. The strongest areas are URL/redirect policy (defense in depth across client, engine, and updater), path/filename containment with opt-in server naming, scanner process execution without a shell, parameterized database access, fail-closed DPAPI secret handling with honest non-Windows degradation, redacted diagnostics/exports, and minisign signature verification with `requireSignedVersion` plus HTTPS-only update endpoints.

The audit identified **four low/informational findings** (F1–F4): a syntactic native-messaging caller check with an inconsistent manifest template, compile-time-only updater key configuration, exclusive-create semantics on the task `.part` file, and a stale comment. None is claimed to be exploitable in this review, and none changes the recommendation that real malicious-input test execution be completed by the parent/QA lane before any release decision. This document is a source-evidence audit, **not a certification**.
