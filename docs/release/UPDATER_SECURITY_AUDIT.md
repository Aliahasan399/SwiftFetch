## 1. Architecture audit

### 1.1 Plugin version
- `tauri-plugin-updater = "=2.14.1"` is **pinned exactly** (`src-tauri/Cargo.toml:23`). An exact pin
  avoids silent minor-version drift in signature/verification behavior.
- Imported and used as `tauri_plugin_updater::{Update, UpdaterExt}` (`src-tauri/src/updates.rs:11`);
  the updater builder is created at `updates.rs:95`.
- The public test vector is attributed to `tauri-plugin-updater 2.14.1` (MIT/Apache-2.0)
  (`updates.rs:555`).

### 1.2 Pubkey configuration
- `plugins.updater.pubkey` is `""` (empty string) in `src-tauri/tauri.conf.json:31`.
- `plugins.updater.requireSignedVersion` is `true` (`tauri.conf.json:31`) — the minisign signature
  must bind the release version.
- `plugins.updater.windows.installMode` is `"passive"` (`tauri.conf.json:31`).
- The **public** key is additionally supplied to the builder via `.pubkey(&publisher.pubkey)`
  (`updates.rs:95`) from `SWIFTFETCH_UPDATE_PUBLIC_KEY` (`updates.rs:57`). Only public-key text is
  ever consumed by the app.

### 1.3 Private key handling
- The signing key is referenced only by the **build/signing environment**, never by application
  source: `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PATH`
  (`tools/build-windows.ps1:23`; `docs/release/UPDATER_KEY_SETUP.md` §3–§4, §7).
- `build-windows.ps1:23` refuses a configured channel if neither signing-key variable is present.
  `UPDATER_KEY_SETUP.md:114-117` prefers `_PATH` so the secret does not appear in process listings.
- The repository `.gitignore` ignores `tauri.key`, `tauri.key.pub`, `*.key`, `*.pfx`, `*.p12`,
  `.env`, `.env.*` (`.gitignore:15-16, 44-49`).
- The owner-run keygen procedure keeps the private key and passphrase offline and out of source
  control, chat, artifacts, and logs (`UPDATER_KEY_SETUP.md:56-92, 181-192`).
- **No private key exists in this workspace** and none was generated by this lane.

### 1.4 Manifest format
- `tools/release-channel.ps1:24-34` writes `artifacts/update-channel/<version>/latest.json` with
  `version`, `notes`, `pub_date`, and a single `platforms."windows-x86_64"` entry containing `url`
  and the base64 `.sig` content.
- Signature binding is enforced at creation time: the `.sig` is read from `<installer>.sig`, base64
  decoded, and must contain exactly one `trusted comment:` line whose `version:<v>` equals the
  `tauri.conf.json` version (`0.1.0`); otherwise the script throws
  (`release-channel.ps1:14-22`).
- Version directories are immutable — the script refuses to overwrite an existing one
  (`release-channel.ps1:30-32`).
- The app parses the manifest with `serde_json` and restores it through the plugin, bounded to
  128 KiB (`updates.rs:116-125`).

### 1.5 Endpoint configuration
- Three **compile-time** variables are read with `option_env!`: `SWIFTFETCH_UPDATE_ENDPOINT`,
  `SWIFTFETCH_UPDATE_ARCHIVE`, `SWIFTFETCH_UPDATE_PUBLIC_KEY` (`updates.rs:55-57`).
- `publisher()` returns `None` unless all three are present, the public key is non-empty, and the
  archive template contains `{{version}}` (`updates.rs:54-61`).
- `safe_endpoint()` enforces: HTTPS scheme, a host, no username/password, no fragment
  (`updates.rs:44-52`).
- `build-windows.ps1:19-25` enforces an all-or-nothing rule (set all three or none); a partial
  configuration fails the build.
- Placeholder expansion for current version / target / arch (and URL-encoded variants) occurs at
  `updates.rs:103-106`; archive `{{version}}` substitution at `updates.rs:59` and `:288`.

### 1.6 Version comparison
- `requireSignedVersion: true` (`tauri.conf.json:31`) requires the signed trusted comment to bind
  the version; enforced at manifest creation by `release-channel.ps1:18-22` and exercised in the unit
  test at `updates.rs:574-575` (manifest `3.0.0` vs signature-bound `2.0.0` is rejected).
- Normal checks use the plugin's default comparator (`rollback = false` at `updates.rs:263`).
- Rollback paths deliberately force `version_comparator(|_, _| true)` (`updates.rs:98`, called with
  `rollback = true` at `:289`, `:295`, `:332`, `:392`) so a signed older release can be restored;
  the rollback package is still signature-verified and its version must equal the installed version
  (`updates.rs:289-297`).

### 1.7 Download
- `package()` (`updates.rs:128-152`) downloads over a 180 s timeout with `no_proxy()`.
- Redirect policy: max 5 redirects, rejects non-HTTPS targets (`:131-135`); the package redirect
  policy additionally rejects embedded credentials (`:133`).
- Size bounds: `MAX_PACKAGE = 128 MiB` (`:15`); `Content-Length` pre-check (`:139`) **and** a
  streaming per-chunk bound (`:145`) prevent a chunked-transfer size bypass. Manifest bounded to
  128 KiB (`:120`).
- Downloaded bytes are signature-verified **before** being returned (`:150`).

### 1.8 Signature validation
`update.verify(...)` is called on every untrusted byte path:
- downloaded update bytes (`:150`),
- existing cached package on reuse (`:217`),
- rollback package after staging (`:297`),
- explicit rollback cached bytes (`:337`),
- recovery-helper loaded update and rollback bytes (`:397` via `load_verified`),
- installer bytes immediately before execution (`:437`).

The public key is bound to the plugin builder (`:95`), and `load_verified()` re-parses the signed
manifest and verifies size and signature (`:390-399`).

### 1.9 Installation
- `start_installer()` (`:347-375`) journals the attempt, writes `health.json` with `healthy: false`,
  copies the **current executable** as a recovery helper (`:348`, `:360-362`), and launches it with
  `--apply-update` (`:363`). The parent app exits only after the helper signals `.ready` (`:367-372`).
- `install_and_wait()` (`:434-463`) verifies installer bytes (`:437`), stages a signed installer,
  and runs either `msiexec /i … /passive /norestart INSTALLDIR={folder}` (`:441-449`) or the NSIS
  installer with `/P` plus `/D={folder}` (`:450-459`). The install folder is derived from the current
  executable and rejected if it contains `"`, CR, or LF (`:447`, `:454`). Exit code `3010`
  (reboot required) is treated as success (`:462`).
- Recovery helper gating (`recovery_requested()`, `:465-533`): requires the `--apply-update` arg, a
  safe `attempt-*.json` name, a canonicalized executable parent matching the staging root, and a
  configured publisher (`:466-474`). Windows-only (`wait_parent`, `:414-432`).

### 1.10 Rollback
- Pre-upgrade: the immutable archive endpoint must supply a signed installer whose version equals
  the installed version; its bytes are downloaded, verified, cached, and re-verified before the
  upgrade proceeds (`updates.rs:285-298`).
- Database snapshot: a consistent SQLite snapshot and path are bound to the attempt (`:301-308`,
  `:349-354`), and restored only if it exists in staging and passes validation (`:401-412`).
- Watchdog/health: on install failure or a failed 180 s health poll, the helper installs the signed
  rollback, restores bound metadata, relaunches the app, and writes `recovery-result.json`
  (`:486-523`). `mark_healthy()` records success only for the matching attempt id and version
  (`:377-385`).
- Explicit rollback re-verifies the cached package before installing (`:325-345`).
- Startup reconciliation rewrites interrupted `installing`/`health` attempts as `interrupted`
  (`:193-208`).
- A 1 GiB staging budget bounds all staged files (`:157-182`).

### Residual considerations / honest limitations
- **No TLS certificate pinning.** Trust relies on the OS trust store and reqwest/plugin TLS. The code
  does not pin a certificate; certificate correctness is delegated to the platform.
- **Compile-time configuration.** Endpoint, archive, and public key are embedded via `option_env!`
  (`:55-57`); changing them requires a rebuild. This is a deployment constraint, not a runtime flaw.
- **Forced comparator on rollback.** `version_comparator(|_, _| true)` (`:98`) intentionally permits
  a downgrade; it is scoped to rollback calls only and is gated by signature verification and an
  installed-version equality check (`:289-297`).
- **`no_proxy()`** may prevent updates in networks that require an HTTP proxy; it is a deliberate
  choice that removes a proxy-based interception path.
- **Manifest authenticity depends on the host.** After the HTTPS fetch, no additional digest or
  second channel confirms the manifest itself; integrity rests on TLS plus the signed installer
  signature (which is verified at install time).
- These are **source-level** findings. None of these protections was exercised at runtime by this
  lane (see §4).

## 3. Key management

- **Owner-controlled production keys only.** The signing key pair is generated locally by the
  release owner using the Tauri v2 signer or minisign, with a passphrase stored in a password manager
  (`UPDATER_KEY_SETUP.md:56-81`). The private key lives only on the owner's trusted machine and is
  backed up offline (`:83-92`).
- **No source control.** Private keys, passphrases, and signed-key material must never be committed
  or placed in tracked files, artifacts, or logs (`UPDATER_KEY_SETUP.md:181-192`; `.gitignore:15-16,
  44-49` ignore `*.key`, `tauri.key`, `*.pfx`, `*.p12`, `.env*`).
- **Public key only in the app.** Only the public-key string is embedded via
  `SWIFTFETCH_UPDATE_PUBLIC_KEY` / `tauri.conf.json` `pubkey` (`UPDATER_KEY_SETUP.md:88-89, 188-189`).
- **Dev/test keys disposable and clearly marked.** The only key material present in source is a
  **public** minisign test vector from `tauri-plugin-updater 2.14.1` used solely by unit tests
  (`updates.rs:555-558`). It is not a signing key, cannot sign releases, and is safe to ship. Any
  owner-created development key should be treated as disposable, clearly labeled non-production,
  and never reused for production signing (`UPDATER_KEY_SETUP.md:151-153`).
- **This lane generated no key** and observed no private key; no production key is exposed here.

## 4. HTTPS channel requirements

- Endpoint and archive URLs must be HTTPS with a host, no embedded credentials, and no fragment
  (`safe_endpoint`, `updates.rs:44-52`).
- Release host URL must be HTTPS without credentials (`release-channel.ps1:9`).
- All redirects are capped at 5 and must remain HTTPS; package redirects also reject embedded
  credentials (`updates.rs:107-112`, `:131-135`).
- `ArtifactBaseUrl` in `release-channel.ps1:9` must be HTTPS without user info.
- Planned GitHub Releases templates are recorded in `UPDATER_KEY_SETUP.md:165-172` and
  `AUTO_UPDATE_EXECUTION_REPORT.md:67-72` as **prepared, not activated**. No host was selected or
  activated by this lane.

## 5. Fail-closed behavior

- With no publisher config, `publisher()` returns `None` (`updates.rs:54-61`); `UpdateManager::new`
  sets `configured = false` and phase `not_configured` (`:67-79`).
- `check_for_updates` returns the snapshot **without any network request** (`:258-275`, `:260`).
- `install_update` and `rollback_update` return `UPDATE_NOT_CONFIGURED` (`:280`, `:328`).
- Any integrity failure (bad signature, bad version, oversized package, unsafe path, failed health
  check) returns a failure/phase `failed` and installs nothing (e.g. `:150`, `:297`, `:337`, `:397`,
  `:437`, `:314-321`).
- A failed helper launch leaves the current app usable and cancels the watchdog
  (`:314-321`, `:365-374`).
- The build fails closed on partial channel configuration or missing signing key
  (`build-windows.ps1:19-25`).

- **Signature verification of a production-signed installer** using the owner's real key.
- **Installation**: NSIS `/P`/`/D` and MSI `INSTALLDIR` behavior, helper readiness handshake, exit
  codes, and relaunch.
- **Failure handling / health check / automatic rollback**: failed installer, 180 s health timeout,
  rollback execution, `recovery-result.json`, metadata snapshot restore.

- Staging budget enforcement, DB backup/restore, and the Windows-only helper path in practice.

## 7. Bottom line

The updater implementation is present in source, pinned to `tauri-plugin-updater 2.14.1`, and
contains layered integrity, size, path, HTTPS, journaling, and fail-closed controls with strong
file:line evidence. Only public-key material and a public test vector exist in the repository; no
private key was generated or exposed. The channel is **not configured** (`not_configured`), no
endpoint was activated, and **automatic updates are NOT operational**. Every real end-to-end claim
(detection, download, install, failure handling, rollback) remains **BLOCKED** on owner actions and a
clean-VM test. This audit makes no claim that the live update path has been verified.
