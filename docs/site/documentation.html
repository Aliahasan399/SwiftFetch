Getting started

  1. Install the WebView2 Runtime and build or obtain a reviewed installer. Current installers are unsigned preview candidates; see Download.
  2. Add an HTTP or HTTPS link, or paste a permitted URL from the clipboard after the confirmation form appears.
  3. Review task details for destination, collision decision and checksum state before the transfer completes.
  4. Use Diagnostics for version information, error codes and local backups.

Use SwiftFetch only for content you have permission to download. Respect copyright, authentication, DRM, paywalls, website access policies and server rate limits.

Backup and recovery

Open Diagnostics → Queue recovery → Back up metadata to create a SQLite backup in the local data folder's backups directory. Keep it private: it contains full URLs, local paths and saved request metadata. A shareable Export queue inventory removes URLs and request credentials but still contains local paths; review before sharing.

A restore pauses active work, validates a separate staging database and saves a consistent safety copy before activation. Restored settings cannot silently re-enable clipboard capture, browser handoff, scanner execution, shutdown requests, schedules or Replace collisions; unfinished tasks become paused or manual. If the main queue cannot open, a startup recovery page offers local backups and a Reset saved proxy action.

A local successful restore does not prove that a damaged disk or failed operating system can be recovered. Keep an independent private backup of important data.

Updates and rollback

The app uses the pinned Tauri updater to verify Minisign signatures, and signed package versions are required. A build without publisher configuration makes no release network request and reports that updates are not configured. The user explicitly checks and confirms updates; the app verifies the currently installed release from an immutable endpoint before accepting an upgrade and caches a rollback package.

Windows Authenticode signing uses a separate publisher certificate configured through the signing overlay; update signing alone does not establish an Authenticode publisher identity. Actual publisher-signed installation and rollback on a clean machine remain external acceptance gates.

Browser handoff setup

The optional extension uses the installed SwiftFetch executable as a Native Messaging host. Build with node browser-extension/tools/package.mjs, use the generated self-contained folder, then register the executable with tools/register-host.ps1. Desktop opt-in and per-user registration are required; unpacked extension setup and native-host registration are optional. The host rejects cookies, unexpected fields and passive capture. See browser-extension/README.md and browser-extension/SETUP.md.

Release and verification status

VERIFICATION.md records local automated and packaged runtime checks and their limits. These are not public-release approval. RELEASE-READINESS.md lists blockers: no code-signing certificate, no selected distribution license, clean-machine install/upgrade/rollback/uninstall test still required, cold-start follow-up, browser store signing/review and publisher update endpoints. VERIFICATION.md also notes that no public upload, store review, 24-hour soak or actual publisher-signed installer update/rollback has been performed.
