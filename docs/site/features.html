Features

SwiftFetch is a Windows x64 desktop application with a React and TypeScript interface in a Tauri WebView2 window and a Rust transfer engine.

Transfer engine

  • Add an HTTP or HTTPS link to queue a download; pause, retry or set transfer limits.
  • The engine probes the source and chooses bounded range requests when the server supports them. Multiple connections are used for eligible files, with a single-stream fallback when range requests are ignored.
  • A dedicated writer writes task-owned working files. Finalization checks file size and any supplied checksum before publishing the result.
  • A user-configured local scanner command can run asynchronously with a deadline. Checksum and antivirus results have limited meanings and do not guarantee that content is safe.
  • Downloaded files open only after an explicit user action.

Queue, scheduling and limits

  • SQLite stores queues, task metadata, schedules, segment checkpoints and settings. An interrupted transfer is reconciled to a recoverable status on startup.
  • One desktop scheduler owns a queue database at a time; a filesystem lock prevents a second scheduler for the same database.
  • Priorities, queue windows, overnight weekdays and a completion or window-end request are supported.
  • Shutdown requests offer a 60-second cancellation countdown before an operating-system request. Windows sleep prevention runs on a dedicated OS thread.
  • Global and per-task limits plus a configured HTTP(S) proxy connection are available.
  • Categories and automatic extension rules choose validated destination folders.

Control and collision handling

  • Task details offer explicit collision decisions: Rename, Replace after explicit confirmation, or Skip. Rename keeps both files; Skip keeps the original and removes only that task's new working file.
  • Verified bytes are not redownloaded. A compatible saved checkpoint can resume after a restart; inconsistent working files restart the affected bytes.
  • History uses cursor queries that filter before limiting, and refresh reconciles all loaded pages.
  • Metadata retention, bounded logs and opt-in cleanup of task-owned failed partials are available.

Backup and recovery

  • Diagnostics can create a consistent local SQLite backup, including queue rows, checkpoints, categories, schedules and settings.
  • A separate queue inventory export removes URLs and request credentials but still contains filenames and local paths; review it before sharing.
  • A startup recovery page appears when the queue or saved proxy cannot initialize. Restores validate the backup in a staging database and preserve the original files in a unique safety folder.
  • Restored settings cannot silently re-enable clipboard capture, browser handoff, scanner execution, shutdown requests, schedules or Replace collisions. See Documentation.

Desktop integration

  • Tray controls can pause work or exit safely.
  • Clipboard capture is opt-in; detecting a URL opens a confirmation form and does not start a transfer by itself. URL drag/drop also opens a confirmation form.
  • The shell provides typed English and Bengali dictionaries with English fallback for untranslated text. It is not fully translated or independently certified for accessibility.

Optional browser handoff

  • Uses a short-lived Native Messaging host that validates one framed intent, checks a local opt-in setting and saves the task for the existing scheduler.
  • Accepts an explicit user gesture, HTTP(S) URL, safe filename, originating page origin, a versioned protocol and a short expiry. Cookies and unexpected fields are rejected.
  • A transaction records a replay receipt and the task together so a repeat request cannot duplicate the operation. The per-user browser host manifest restricts which extension can launch the host.
  • When the desktop app is closed, the queued task remains until it opens.

Signed updates and rollback

Updater code supports publisher-configured signed-version checks, verified rollback preflight, an installer helper and health monitoring. An unconfigured build makes no release network request. Actual publisher-signed installation and rollback on a clean machine remain untested release gates. See Documentation.

Scope boundary

The initial delivery targets HTTP and HTTPS on Windows. Torrent, FTP, cloud sync, media extraction, remote control and mandatory online licensing are outside the initial product. Download speed depends on the source, connection, server policies, storage and device resources; multiple connections are an optimization and do not guarantee a particular improvement.
